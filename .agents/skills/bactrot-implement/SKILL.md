# BactRotAnalyzerの実装

受入条件を満たす変更を、他タスクと分離して既存PRまたは新規1本のPRへまとめる。適用される `AGENTS.md` を読み、科学的制約・実験データ非公開・PR成果物整理・GitHub Codexレビュー回数の規則に従う。本skillは兄弟skillの導入を必須にせず、権限・マージ承認・外部投稿の許可を追加しない。

## 着手と再開

- 全体の入口、分野親、対象Issue、最新の重要コメント、直接の依存、関連PR、Development、Kanbanを確認する。目的・範囲・対象外・受入条件・優先度・期限（確定/暫定/未定）を把握し、研究側の目標への影響を見る。初回は全体を読み、再開時は変更された要件と実状態を中心に確認する。
- 同じIssueの既存PRとブランチを探す。あればそのPRへ修正を追加する。なければ最新の基準ブランチと既定ブランチを確認し、リポジトリ規則に従うブランチを作る。既定は `codex/` 接頭辞。管理専用の親へ空PRを作らない。
- 編集前に作業領域・ブランチ・base/head SHA・未コミット変更を確認する。並列タスクは別ブランチと別worktreeに分離する。適切な専用worktreeは再利用し、なければ利用可能な `create_worktree` 等で作成する。共有チェックアウトに他作業の変更がある場合、そこで編集・checkout・reset・commitせず、専用領域へ移る。他作業の変更や実験成果物を取り込まない。
- 変更予定ファイルと共有入出力の担当を明示する。共通ファイルは編集担当を一つにし、他担当へ必要な変更は該当Issueへ要点を渡す。共有仕様を変える場合は消費側への影響・互換性・統合順を確認する。
- 中断後は記憶だけで再開しない。リモートPRの状態・base/head SHA、ローカルブランチとHEAD、未コミット差分、CI、レビュー指摘、未完事項を読み直す。PRがマージ済み・headが移動済みなら、その実状態に合わせて残作業を判断する。

## 実装と検証

受入条件内の可逆な実装判断・整理・修正・検証は自律的に進める。作業中の要件変更を現在の受入条件と照合し、矛盾を黙って解消しない。目的・受入条件・優先順位の大きな変更、科学的測定や解釈、重要なトレードオフ、権限外の操作、既存規則が要求する承認だけは推奨案と影響を添えて確認する。通常の実装詳細は聞き直さず、重要な回答待ちでも依存しない作業を続ける。時間経過を承認とみなさない。

- 変更の影響に応じた検証を選び、必要なCIを満たす。解析変更では元フレーム・時刻・欠測、画像空間のCW正、V2主系列と停止測定の分離を確認し、公開可能な合成データを使う。文書・skillのみなら形式、参照、代表ケースを中心に確認する。
- 成功済みで無関係な検証を理由なく繰り返さない。追加変更・base更新・新しい失敗や未解決の懸念があれば、その影響に必要な確認を行う。成功・失敗・未実施・環境上実行不能を区別し、結果を対象headへ結び付ける。
- CI失敗はログと差分、必要なら同じ環境のbaseでの再現から「自身の変更」「既存不具合」「環境問題」に分類する。分類不明なら推測で既存扱いにしない。範囲内の原因は修正し、受入条件達成に必要な修正を別Issueへ先送りしない。
- 範囲外の独立不具合は既存Issueを探して再利用し、なければ再現条件・影響・根拠を別Issueへ整理する。環境問題は失敗箇所と解除条件を示す。いずれも失敗したCIを成功扱いにせず、必要なチェックを満たせない状態とマージ条件を明示する。

## PRとレビューへの受け渡し

[PRテンプレート](../../../.github/PULL_REQUEST_TEMPLATE.md)を使い、解決する問題・変更後の動作・対象Issue・検証・重要な限界を基本日本語で記す。1実装Issueにつき1 PRを維持し、Developmentの実際の紐付けをUIまたはAPIで確認する。単なる番号記載や `Closes` の文言で成功と判断せず、baseと既定ブランチの違いを考慮する。確認できなければ未確認と記す。

レビュー依頼前とマージ前に完全なPR差分を読み、一時ヘルパー・作業ログ・ローカル固定パス・不要な依存や参照を整理する。恒久的な仕様・回帰テスト・実行手順・検証根拠と他作業の実験成果物は保持する。GitHub Codexレビューは既存履歴を確認して原則1回とし、追加依頼は適用される `AGENTS.md` の明示承認条件に従う。

自己テスト成功は独立レビュー完了ではない。レビュー対象SHA、未解決指摘、最新headのCIを区別して渡す。head更新後は前回指摘・新規差分・関連影響を確認し、古いheadのレビューを最新と表示しない。実施していない独立レビューを成功扱いにせず、必要なレビュー条件は保留のまま示す。

報告は重要な変更・影響・検証の要点・未解決事項に絞る。現在の合意はIssue本文、重要判断の理由はIssueコメント、実装・検証根拠はPRへ置く。定常の報告書・作業日誌を増やさない。引き継ぐ情報は対象Issue/親、PR、作業領域/ブランチ、base/最新head SHA、変更範囲、検証結果、残課題、依存と期限の必要な差分とする。

実際のマージと受入条件、Issue・親の進捗・Kanbanの整合を確認するまで完了扱いにしない。既存の権限・承認条件でマージを判断し、条件未充足なら理由を示す。マージ後は最新の優先度・期限・依存・担当状況から次Issueと短い理由、そのまま使える日本語プロンプト（対象/親/全体のリンク、目的・範囲・受入条件、関連PR、前提と制約）を提示する。次タスクの自動開始・別チャット作成・他チャットへの送信はしない。
